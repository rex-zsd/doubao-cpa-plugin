# 2026-10-18 工具路由延迟修复

此分支基于线上 0.3.9（3913f51），首次路由优化发布为本地 0.3.11。后续 0.3.12 的收尾延迟优化见 [LATENCY_0312_CN.md](LATENCY_0312_CN.md)。没有合入尚未提交的 0.3.10 重发实验。

## 线上证据

线上 CPA 访问日志与插件私有任务记录相互对应：2026-10-17 19:11:39–19:15:01，doubao-orange-5.5 的首轮工具请求耗时 3 分 22 秒。该任务携带 32 个客户端工具，reasoning_effort=7。在第一个真实 MCP Bash 调用之前，模型误用了 6 次 computer_use_tool 和 4 次平台内置 Bash，插件均拒绝；模型随后才找到调用方的 MCP Bash。后续两个调用分别约 9.2 秒，最终回答约 7.5 秒。

另一轮没有错误路由的同模型任务，单次请求约 8–50 秒。这部分还包含上游推理、工具发现和客户端结果交回等待，不能归因于插件代码。

## 修改

- 把当前轮的完整 MCP 工具名与执行环境说明放在对话记录之后，避免长历史把路由说明隔在前面。
- 明确说明平台内置 Bash、computer_use_tool 和 Python subprocess 在适配环境中不可用，反复重试或变更权限不会解决。
- 拒绝错误工具调用时，直接提供本轮可发现的 MCP 完整名称；同名客户端工具优先给出对应名称，批处理模式只给出 client_tools_batch。
- 仍然拒绝未声明的工具、错误连接器和内置执行请求。没有把内置调用自动转换为客户端命令。

模型、思考强度、工具集合、重试配置、任务恢复和函数调用语义保持原设置。

## 验证

Go 1.26：go test -race ./... 和 go vet ./... 通过。新增回归覆盖内置 shell、computer_use_tool、错误连接器与批处理模式下的拒绝和路由提示，确认没有创建客户端调用。

对照测试使用线上同一套 32 个工具定义、doubao-orange-5.5、reasoning_effort=7，要求调用一次 Bash 并回答随机校验串。测试端只回传校验串，不执行模型生成的 shell 命令。原始生产请求和凭据未写入此报告。

优化前两次：首个调用 26.549 / 20.861 秒，结果交回后的回答 7.380 / 6.873 秒，均通过。小型探针没有复现生产长对话中的 10 次错误路由，因此不能用它证明该故障已完全消除。

优化后两次：首个调用 17.369 / 16.271 秒，结果交回后的回答 8.118 / 6.951 秒，均通过。模型和参数相同，前后每组仅 2 次，不能代表所有负载，也不能证明生产长对话中的错误路由已经完全消除。
