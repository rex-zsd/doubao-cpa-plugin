# 豆包 Work 原生工具实测（2026-10-18）

这是正式接入前的隔离实验记录。后续 0.3.19 已接入并上线兼容子集，配置、恢复、并行及线上对照见[原生工具接入与上线验收](NATIVE_TOOL_ROUTING_CN.md)。下文关于 0.3.18 未改动的描述指实验当时。

原生工具通道可以接入现有客户端工具循环。隔离原型已实际收到结构化 Read/Bash 事件，将调用交给 HTTP 客户端执行，再按原生工具协议上传真实结果；无需把函数调用解析成模型输出的 JSON 文本。

这次验证的是 Work Agent 的原生工具通道。底层仍运行 Work Agent，完整历史仍按现有机制传入；没有发现或验证可绕过 Agent 的纯模型工具 API。

实现位于独立实验分支，代码提交 `d15d120`。只有独立 helper 的显式开关 `-native-tools-probe` 能启用，正式插件没有启用入口。

实测路径：

```text
Orange 5.5 / Work Agent
  → 原生 Read 或 Bash 结构化事件
  → 适配器按调用方完整 schema 校验、关联原生调用 ID
  → OpenAI tool_calls 返回 HTTP 客户端
  → 客户端实际读文件或执行限定命令
  → 原生 content / isError / tool_input 结果回传
  → 原来的同一次 Work 任务继续，读回并核对最终回答
```

发现并处理了两个实际协议差异：

- 原生 Read 会携带 `thumbnail_size=full`，原客户端 Read schema 没有这个字段。验证版限定为绝对路径的 `.txt` 文本文件，仅移除此无效的缩略图显示字段；`file_path`、`offset`、`limit` 原样转发，offset 为 0 等不兼容情况仍回退 MCP。
- 原生 Bash 会携带 `sandbox_permissions=use_default`，原客户端 Bash schema 使用另一套权限字段。验证版仅接受原生默认权限，不改写客户端权限策略；不把提权请求转换成客户端的危险执行选项。命令和毫秒超时原样保留，后台及提权等情况仍回退 MCP。

除这两个明确列出的默认字段外，不丢弃任何未知字段。原始原生 `id`、`name` 和 `input` 保留，用于结果关联；客户端收到的函数参数仍必须通过其原始 schema。原生结果使用顶层 `content/isError`，MCP 结果继续使用 `raw_result`，二者不能直接混用。

验证使用 Orange 5.5、effort 7，以及线上请求留存的全部 32 个原始工具定义。没有删减工具说明、schema 或历史，没有降低模型和推理等级。原生 Read/Bash 的完整调用方说明与 schema 另行给出，避免模型只看到平台自带工具的不同参数说明。

| 场景 | 实际验证内容 |
|---|---|
| 文本 Read | 读取真实测试文件第 2 行，limit=1，最终值与文件内容逐字核对 |
| 前台 Bash | 客户端执行白名单里的固定 Python 命令；随机值在命令真正运行后才生成，模型事先不知道 |
| 依赖链 | Read 返回未在提示词中透露的命令，随后 Bash 必须使用这个真实结果，依次执行一次 |
| 失败 Bash | 命令真实退出 7，stderr 原文及错误标志回传，核对最终失败回答 |
| 重试与关联 | 每个工具阶段重放相同 HTTP 请求，要求返回同一调用且客户端只执行一次；上传结果 ID 与原生 ID 一致 |
| 默认行为 | 本地回归验证关闭开关时仍拒绝原生转发；未知参数、不兼容媒体/权限等不能绕过 MCP |

初始未适配默认字段的两次探测均回退 MCP，虽然最终回答正确，**不计为原生成功**。修正后按实际事件名称、结果 DTO 和 denied 次数单独核验原生路径，避免混淆。

第一次失败命令测试的真实错误和随机 stderr 都正确，最终输出仅在 `FAILED:` 后多了一个空格，因此严格文本比较失败。这条记录保留；将提示词明确为冒号后不留空格后，原生复核通过。没有通过改写错误内容或降低错误检查来掩盖失败。

同条件小样本耗时如下，均以秒计；每行的样本数为每条路径各自的次数。

| 场景 | 每路次数 | MCP 首次工具 / 总耗时 | 原生首次工具 / 总耗时 | 总耗时减少 |
|---|---:|---:|---:|---:|
| 文本 Read | 2 | 22.2 / 30.0 | 10.2 / 16.9 | 44% |
| 成功 Bash | 2 | 26.5 / 35.3 | 11.3 / 22.7 | 36% |
| Read → Bash 依赖链 | 1 | 18.6 / 45.9 | 11.8 / 29.5 | 36% |
| 失败 Bash（明确输出格式） | 1 | 23.7 / 31.4 | 11.1 / 19.6 | 38% |

Read/Bash 的数值是各 2 次的中位数；依赖链与失败场景各 1 次。初始回退探测及旧提示下的空格差异没有混入上述性能比较，完整记录仍在附件中。

耗时为客户端开始请求到首次收到工具调用、以及到最终回答的墙钟时间，包含真实客户端操作及相同的 HTTP 重放检查。MCP 与原生比较均在同一个独立 helper 二进制、同一独立设备标识、相同 32 工具/模型/effort 下运行；两边都使用每任务连接器。顺序为原生、MCP、原生，减少仅比较不同时段的影响。正式 0.3.18 开启了连接器缓存，因此这里的差值不能直接当作线上收益。

这是小样本协议验证，不能外推到所有编码任务的质量、p95 或长期稳定性。已证实的结果是这些真实调用及结果一致；尚未验证 PDF/图片 Read、其他文件类型、Write/Edit/Grep 等原生工具、后台进程、权限升级、原生并发和长任务恢复。32 个原工具仍完整保留，这些能力继续使用 MCP。

共完成 15 次真实任务：2 次协议校准、7 次原生路径验证（含一次仅输出空格不同的记录）、6 次 MCP 对照。7 次原生路径均正确回传实际结果；其中 6 次通过逐字比较，另一次仅冒号后多一个空格，明确格式后复核通过。所有任务均只提交一次生成、保留全部工具、完成连接器清理；原生调用 ID 与结果 ID 关联一致，HTTP 重放没有造成客户端重复执行。

本地验证通过 `go test -race ./internal/doubao -run "TestNativeProbe|TestRejectedNativeTools|TestNativeToolScope" -count=1` 和 `go test ./...`。实验 helper SHA-256 为 `e9e1e780c5b4d572b122033ca5c8e51326f39bc28b59abecb7687951f17ba6a7`。

正式 0.3.18 插件与配置的 SHA-256、容器 ID 均与测试前一致；容器启动时间早于测试，未在测试期间重启。使用独立测试设备标识，不与正式设备共用工具事件通道。测试活动任务和待清理连接器均为 0；独立 helper 已退出，测试端口已关闭。正式服务没有启用该实验。

下一步适合按工具逐项建立能力映射：原生兼容子集直接转发，其他函数保留 MCP，先补齐真实客户端的媒体、文件编辑和后台任务契约与回归，再考虑正式接入。当前结果支持继续走这条路线，暂不足以把全部客户端工具切到原生。

可复核附件为 `results-sanitized.json`；每次生成次数、原生工具名称、结果上传/关联、工具定义完整性、错误状态和分段耗时均有记录，不包含凭证、用户原始提示、工具输出或推理正文。完整私有回执仅留在隔离测试目录。
