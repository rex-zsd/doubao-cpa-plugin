# 长历史分段预发（0.3.33）

Work 单条消息最多 262,144 个 UTF-16 字符。此前，渲染后超过这个长度的请求会直接返回 `context_length_exceeded`。而官方 API 的上下文要大得多，长线程（例如反复运行的定时任务线程）因此在这里失败。

不过，这个上限只针对单条消息。同一个 Work 会话可以容纳多条消息，模型能看到之前的全部内容。

## 做法

1. 超长请求先找出能装进一条消息、并且紧跟在一条普通回答之后的最长尾部。
2. 尾部之前的历史按新请求的方式渲染成 JSON 记录，切成若干段（最多 8 段）。每段作为一条独立消息发进同一个 Work 会话，并要求模型只回复「收到」。附件替换为编号标记，随所在段一起上传。
3. 最后一段答完后，这个会话按调用方的历史重新登记。调用方的请求随即作为普通续写发出，只发送尾部。后续轮次照常续写。

分段沿用调用方的模型、工具和推理设置，所以带工具的请求也落在同一个工具会话里。如果模型在分段时仍然调用工具，会收到「不能调用工具」的结果，最多两次。

## 不悄悄丢内容

窗口较小的模型会被 Work 截断：上下文回落，或者几乎不再增长。所以每段都必须让 Work 报回的上下文至少增长该段估算 token 的 40%。达不到，或者 Work 没有报回上下文时，就丢弃这个会话，照常返回 `context_length_exceeded`。

## 实测

- 容量（同一会话分段发约 225K 字符的日志，最后询问埋在各段里的标记）：
  - gpt-6.1-sol：约 500K token 内全部答对，超过后最早的内容被整段丢弃。
  - deepseek-v4.1-flash 和 2.1-pro：上下文停在约 170K–210K token。
- 0.3.33 隔离实例：
  - 一次发出约 687K 字符：gpt-6.1-sol 分 2 段加尾部，37–53 秒，3/3 标记答对。
  - 带工具：标记正确写进函数参数，工具回合正常续写。
  - 第一段附带的图片颜色答对。
  - deepseek-v4.1-flash 在第 2 段检测到上下文回落，29 秒内返回 `context_length_exceeded`。

日志事件：`GATEWAY_PRELOAD start/segment/done`、`GATEWAY_PRELOAD_FAILED`、`GATEWAY_PRELOAD_SKIPPED`。
