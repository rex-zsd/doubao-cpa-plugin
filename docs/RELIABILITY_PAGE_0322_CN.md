## Work 重发合并

Work 只等每个客户端函数约 1 分钟，之后以新的调用编号再发同一个调用。0.3.21 及更早的版本逐个处理调用，客户端交回前一个结果后，马上把重发的调用交给客户端，同一个函数执行两到三次。

0.3.22 在调用帧到达时登记它，直到它的结果上传给 Work 为止都算“未答复”。名字和输入都相同（连接器参数按 JSON 值比较，不比较编码）的调用，如果在原调用未答复时到达，就记为原调用的重发。轮到处理它时，直接上传原调用的结果和错误标记，不交给客户端。原调用答复之后才到达的相同调用是新的调用，照常交给客户端：Work 可以合理地重复调用同一个函数，现有的同参数依赖链回归仍然通过。

登记不落盘。重启恢复后，日志里未上传的调用帧会重新登记，但重启前已经到达的重发可能再执行一次。

离线回归：重发复用原结果和错误标记、不产生第二个对外调用；答复后到达的相同调用照常执行；参数编码不同但值相同时仍判为同一调用。去掉合并逻辑后，第一项测试会失败。

线上实测在隔离实例上进行，模型为 Orange 5.5，工具为一个查天气的客户端函数：

| 场景 | 结果 |
|---|---|
| 客户端等到重发到达后才交回结果（约 65 秒） | Work 在原调用后 65.1 秒重发一次。插件合并，两次调用都上传了同一结果，客户端只看到 1 次调用。交回后 7.5 秒给出最终回答，回答用上了工具结果。 |
| 客户端 130 秒后才交回 | 重发到达一次。原调用发出约 130 秒后，Work 结束运行，结果在此之后才到，回答没有用到它。 |

第二行说明，客户端函数仍应在 1 分钟内交回结果，超过约 2 分钟时 Work 不再等待。这与合并无关。

## 断流续接

0.3.21 中，回复流读失败（日志为 `SSE read failed`）会让任务以 409 `upstream_failed` 结束，尽管 Work 仍在运行它。0.3.22 对 Work 已确认受理（ACK）的运行：

- 异步任务流断开，或结束时没有终止事件，从保存的游标重新订阅，最多再订阅两次，游标之前的事件跳过。
- 之后，或主回复流本身断开时，改为回读跟进，直到拿到最终回答。
- 任何情况下都不因断流再发起生成。

ACK 之前断开仍然失败，因为无法确认 Work 是否已受理。

离线回归覆盖：ACK 后主回复流断开、ACK 前断开、异步流从游标续订且不重复观察事件、反复断开后退回回读、无终止事件的流续订，以及 ACK 和最终回答落盘的时机。

线上实测使用 helper 的测试钩子 `DOUBAO_HELPER_TEST_DROP=<路径>:<事件数>`。它只在 helper 的 serve 模式里生效，在指定数量的 SSE 数据事件后断开该路径上的第一个响应，插件本身从不安装它。模型为 Orange 5.5：

| 场景 | 结果 |
|---|---|
| 聊天模式，主回复流在第 3 个事件后断开 | 改为回读，6.2 秒得到正确回答，1 次生成 |
| 带工具任务，ACK 后马上断开（第 3 个事件） | 工具调用照常下发，交回结果后得到用上结果的回答，1 次生成 |
| 带工具任务，运行中断开（第 12 个事件） | 同上，1 次生成 |
| 断在 ACK 之前 | 任务按原方式失败，回执中没有任何事件 |

当前 Work 的带工具任务和聊天模式都只使用主回复流：ACK、正文分片、等待工具期间的心跳、整条消息通知和三次结束事件都在主回复流上，没有异步任务流。游标续订因此只有离线测试覆盖。

## 回执写盘

回执带着完整请求，工具目录大时有几百 KB。此前每收到一个事件就整份写盘并同步。0.3.22 只在持久状态变化时写盘：发出、ACK、新增任务、终止事件、完成，游标进度最多每秒写一次。按 0.3.19 调研测得的单次快照耗时（7–11 毫秒）和每个任务 23–31 个事件估算，每个短任务可省约 0.1–0.3 秒。本批没有单独实测这一项。

## 插件页面

插件声明了 CPA 的 `management_api` 能力。CPA 管理面板的插件菜单里出现「豆包 Work」，页面地址为 `/v0/resource/plugins/doubao-work/console`。CPA 不对资源页面鉴权，所以页面里不带任何数据：它请用户输入 CPA 管理密钥，再通过以下需要管理密钥的接口读取。

| 接口 | 作用 |
|---|---|
| `GET /v0/management/doubao-work/status` | 版本、原生工具开关、登录状态和上次校验时间、运行中任务数与上限、最近请求、近 24 小时按原因分类的结果、断流续接与重发合并次数、模型列表 |
| `GET /v0/management/doubao-work/tasks` | 运行中和约 30 分钟内结束的任务：模型、模式、等待的客户端函数及已等时长、剩余期限、调用次数、结果 |
| `POST /v0/management/doubao-work/tasks/cancel` | 取消运行中的任务 |
| `POST /v0/management/doubao-work/login/start` | 开始扫码登录，返回二维码图片 |
| `GET /v0/management/doubao-work/login/status` | 扫码进度 |
| `POST /v0/management/doubao-work/test` | 用指定模型发一句话，返回回复、首字时间和总耗时 |

接口只返回状态、计数和耗时，不含提示词、工具参数、工具结果、回答或登录会话。页面设置了内容安全策略：只连接同源接口，不加载外部资源，只允许同源嵌入。管理密钥默认只保存在当前标签页。

取消走插件内部的替换路径：停止 Work 的运行，正在等待的客户端收到 409 `task_cancelled`，任务标记为结束。之后交回这个任务的工具结果时，插件按完整对话开新任务，不再像外部取消 Work 运行后那样返回 409。

离线回归覆盖：注册的路由都在需要鉴权的管理前缀下，资源只有页面本身；页面不含数据，打开页面不会加载服务；没有服务时接口的返回；任务和统计只含元数据（测试中提示词和工具结果都不出现在接口数据里）；取消后迟到的工具结果开新任务。

线上实测使用一个临时的官方 CPA v8.0.13 实例（与线上相同的镜像），加载 0.3.22 候选版本和隔离会话：

| 检查 | 结果 |
|---|---|
| 管理面板插件列表 | 列出菜单「豆包 Work」，路径正确 |
| 不带密钥打开页面 | 200，带内容安全策略 |
| 不带密钥读状态 | 401 |
| 带密钥读状态 | 版本 0.3.22，登录正常，模型列表和统计正确 |
| 测试按钮（豆包 2.1 Lite） | 首字 1.8 秒，总耗时 4.0 秒，回复正确 |
| 带工具任务挂起后查看任务列表 | 显示等待客户端函数 get_weather、模式、模型和剩余期限 |
| 取消该任务 | 结果为 task_cancelled |
| 取消后交回工具结果 | 200，开新任务，9.2 秒得到用上结果的回答，没有 409 |
| 统计 | 成功 2，已取消 1 |
| 开始扫码登录 | 返回 5,045 字节的 PNG 二维码，状态为等待扫码，未扫码 |

页面用模拟数据在桌面和手机宽度、浅色和深色主题下截图检查，没有横向溢出和脚本错误。

## 未做：带工具时正文流式

计划中的“带工具时正文先流式”实测后决定不做。用同一个任务（依次查两次天气，再写 300–480 字总结）记录了三个模型的正文块结构，只记块类型、长度和时间，不记内容：

| 模型 | 最终回答 | 提前可见 |
|---|---|---|
| Orange 5.5 | 478 字在结束前一次给出（1 个分片） | 无 |
| 豆包 2.1 Pro | 451 字分 42 片，用时 4.9 秒 | 约 5 秒 |
| GPT-6 Astra | 319 字分 17 片，用时 3.6 秒 | 约 4 秒 |

三个模型都会在工具调用前先输出一段说明。这段说明在最终回读里被折叠，不属于最终回答。要流式输出，就得把它作为工具调用消息的正文发给客户端，并据此核对续接历史。这会改变工具调用消息的格式，经 CPA 转换后续接能否对上，只能用真实 Claude Code 验证。收益最多几秒，Orange 5.5 没有收益，所以暂不改变。
